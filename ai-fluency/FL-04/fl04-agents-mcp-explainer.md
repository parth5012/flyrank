## 1. What an agent actually is (in my own words)

A chatbot answers one prompt with one response. An **agent** closes a loop: it takes a goal, looks at the current state of the world, picks a tool to act with, reads the result, and decides what to do next — repeating until the goal is done or it gets stuck and asks for help. The loop is *perceive → decide → act → observe*, and the key property is that the **model chooses the next step at runtime** instead of following a path a programmer fixed in advance.

Three things have to be present before I call something an agent. First, **autonomy over steps**: given "clear my unread backlog," it decides whether to list mail, read a message, label it, or skip it — I did not hardcode that order. Second, **tool use with feedback**: it calls real functions (APIs, file writes, queries) and the observation from each call changes its next decision. Third, **a termination rule**: it knows when to stop — goal reached, budget spent, confidence too low — and says so instead of looping forever. A system with all three earns the name. A system with a fixed sequence of LLM calls, however clever each call is, does not — that is a workflow wearing an agent costume, and the distinction matters because the failure modes are completely different. Workflows fail when a step's input drifts; agents fail when the loop itself misjudges, repeats, or burns budget.

## 2. Workflow vs agent — and what my FL-04 pipeline is

A **workflow** is a path I draw in advance: step A always runs, then step B, with fixed branches I wrote. The model may do smart work *inside* a step, but it never reorders the steps. An **agent** gets the goal and the toolbox and draws its own path per run, including paths I never imagined.

My FL-04 pipeline — the Books to Scrape scraper in this repo (`backend/Assignment 5`: catalogue pages → fetch → parse with BeautifulSoup → validate with Pydantic → repair once → quarantine failures → write `books.json` + `run-report.json`) — is **a workflow, clearly**. Every run executes the same stages in the same order; retries happen exactly once and only for timeout/5xx; a 404 is never retried by design. There is no step where the model surveys state and picks a different strategy. That rigidity is a feature: it gives me idempotent output (60 records every run), a 0.5s politeness guarantee, and a failure-isolation promise (one broken page never kills the run). An agent would be free to, say, re-crawl everything because one price looked odd — my pipeline cannot, and my evaluation depends on it not doing so.

## 3. What MCP is, and its three primitives

The Model Context Protocol is an open standard for plugging external capabilities into an LLM app without custom glue per integration — often described as "USB-C for AI context." The app I chat in is the **host**; the connector inside it is the **client**; each external capability is a **server** speaking JSON-RPC with capability discovery. I read the current spec (2026-07-28) to write this, and the core idea is small: servers expose exactly three primitives. **Tools** are functions the model can call (`tools/call`) — they *do* things: query a DB, hit an API, write a file. The model decides when to call them, and calls can need my approval. **Resources** are read-only data the app feeds the model as context (`resources/read`) — file contents, schemas, records — addressed by URI, with templates for parameterized reads. The app, not the model, controls which resources are attached. **Prompts** are reusable instruction templates (`prompts/get`) that bundle a task pattern with the right tools and resources, invoked explicitly by me. Concretely: a database server can expose the schema as a resource, querying as a tool, and a "weekly-report" analysis pattern as a prompt — context, action, and procedure kept separate so each side stays honest about who chose what.

## 4. One concrete upgrade that would make FL-04 an agent

My pipeline needs exactly one architectural change to cross the line: **replace the fixed stage order with a model-driven control loop over the same toolbox**. Today the orchestrator calls fetch, then parse, then validate. In the agent version, the model would see the goal ("60 valid records, no extra requests, politeness respected") plus live state (cache hits, failures so far, run-report deltas) and choose each next tool call itself — e.g., noticing three detail pages failed with the same selector, hypothesizing a DOM change, and choosing to re-inspect one page's HTML before rewriting the selector, rather than following my hardcoded "repair once then quarantine" rule. Everything else — the tools, the validators, the politeness budget — stays identical; only *who picks the next step* changes from me-at-build-time to the model-at-runtime, fenced by a step budget (say, 40 tool calls) and a stop rule (all 60 valid, or report shortfall and quit). That single change converts deterministic replayability into adaptive recovery — the honest tradeoff my proof statement ("reliable at scale") would then have to evaluate.
